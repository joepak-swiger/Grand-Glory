# Testing and browser evidence

Run `npm install`, then `npm run typecheck`, `npm run test`, `npm run build`, and `npm run test:e2e`. Playwright needs Chromium (`npx playwright install chromium`). CI installs Chromium with its Linux system dependencies before browser tests.

Latest local verification on the horde branch: `npm run typecheck` passed, `npm run test` passed all 44 tests, `npm run build` succeeded, and `npm run test:e2e -- --workers=1` passed both Chromium scenarios. At commit `c191a9c379cfa31d3c1bdccc147019560671f75d`, both the GitHub push workflow and PR workflow passed, including install, typecheck, unit tests, production build, Chromium installation, and both browser scenarios: [push run](https://github.com/joepak-swiger/Grand-Glory/actions/runs/41771478450), [PR run](https://github.com/joepak-swiger/Grand-Glory/actions/runs/41771483733). Automated browser testing does not constitute human playtesting.

Vitest covers deterministic simulation including movement, boundaries, targeting, cooldowns, hit detection, health and invulnerability, enemy knockback, spawn bounds/distribution/reproducibility, death/XP, leveling and pending choices, upgrades, boss attacks/telegraphs, pause, end states, restart, visual metadata, seeded behavior, and cleanup. Horde coverage includes multi-spawn batches, surge timing, ranged enemy windups and volleys, heavy enemy stats, target caps, upgrade evolution requirements, and camera-adjacent spawn distribution.

The Playwright suite runs the actual Vite application in Chromium. At `/?test=1`, a deterministic accelerated scenario shortens the run for repeatable checks; it is not human testing or a normal-length run. It checks real portrait and sprite assets, frame advancement, facing/mirroring, combat, upgrade choice and effect, pause, boss, victory, defeat, restart, console/page errors, and failed asset requests. A separate `/?test=normal` scenario uses the standard run configuration and ordinary natural spawns, without injected XP or enemies. The browser harness advances fixed simulation steps while Chromium renders, resolves actual upgrade UI, observes the 2:30 boss, and continues until a terminal result beyond the 3:00 target. This is standard-config automated browser testing, not a wall-clock three-minute session or human playtest.

Browser evidence is captured in `artifacts/evidence/` by `npm run test:e2e`, including title, standing/moving Blue Pinwheel, left-facing Blue Pinwheel, mixed enemy facing, active combat, upgrade choices, boss, victory, and defeat. `13-standard-victory.png` is captured from the standard-config natural-spawn scenario. Evidence is only valid when generated by the actual browser suite; it is not synthesized from the test setup.

Current simulation-only measurements in Node 24 (300 fixed steps, median elapsed time) are: 25 enemies 4.23 ms, 50 10.10 ms, 100 22.58 ms, 150 39.89 ms, and 200 51.71 ms. These measure simulation work only, not rendering. In the latest local Windows headless Chromium standard-config run, rendering was approximately 20 FPS (50 ms/frame) early at 14 active enemies and 30 FPS (33 ms/frame) late at 40 active enemies. These rendering samples are environment-specific and are not a representative GPU benchmark; hosted CI uses a different CPU-rendered environment. Automated browser runs are not human playtesting.

With the initial 760-HP boss, the standard-config browser scenario reached 4:00 with 252 boss HP remaining and the player alive, so that version ended in an overtime escape. Boss health was tuned to 460; rerunning the same standard configuration naturally reached victory at 3:58 with 138 kills, level 10, and about 152 of 190 HP. This is automated test-driver balance evidence, not a human playtest.
